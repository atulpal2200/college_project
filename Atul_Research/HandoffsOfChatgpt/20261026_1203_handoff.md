# Project Handoff: AI-Based Personalized Quiz Generation & Evaluation System

**Prepared:** 2026-10-26  
**Purpose:** Consolidated handoff of project discussions, decisions, research direction, architecture, and open questions.

---

## 1. Project Overview

**Project:** AI-Based Personalized Quiz Generation and Evaluation System  
**Team:** 3 members  
**Context:** Academic/final-year project

The system generates multiple-choice questions (MCQs) from professor-provided educational material, evaluates their quality, keeps a professor in the approval loop, supports quiz assignment and deterministic scoring, and eventually provides topic-level performance analysis and personalized practice.

### Long-term workflow

```text
Educational Material
        ↓
Content Extraction
        ↓
Chunking + Embeddings
        ↓
Vector Retrieval (RAG)
        ↓
LLM-Based MCQ Generation
        ↓
Structural + Quality Validation
        ↓
Professor Review and Approval
        ↓
Question Bank → Quiz → Assignment
        ↓
Student Attempt
        ↓
Deterministic Scoring
        ↓
Topic-Level Performance Analysis
        ↓
Personalized Practice
```

## 2. Scope and Product Decisions

### Current MVP

The semester MVP is professor-facing and limited to MCQ generation and quiz preparation.

- Upload PDF or text material.
- Extract and process document text.
- Generate MCQs grounded in uploaded material.
- Validate generated output.
- Evaluate question quality with AI-assisted checks.
- Allow the professor to edit, reject, or approve questions.
- Maintain an approved question bank.
- Create quizzes from approved questions.
- Assign quizzes to a whole class or selected students.
- Support student attempts and deterministic MCQ scoring.
- Provide basic results/performance information.

### Future scope

- Topic-level strong/weak area identification.
- Personalized practice quizzes.
- Rule-based personalization using accuracy, attempt count, and recent performance.
- Experiments with fine-tuned open-source models alongside RAG.
- More advanced psychometric evaluation if justified by time and data.

### Scope guardrails

Do not turn the MVP into a full LMS, social platform, complex recommendation engine, or unnecessarily distributed microservice system. Keep the implementation feasible for a three-person team.

## 3. Roles and Functional Requirements

### Professor

1. Upload PDF/text material.
2. Generate MCQs from the material.
3. Review, edit, reject, and approve generated questions.
4. Maintain a question bank.
5. Create quizzes from approved questions.
6. Assign quizzes to a class or selected students.
7. Review student marks and, later, topic-level performance.

### Student

1. View assigned quizzes.
2. Attempt and submit answers.
3. Receive marks according to configured feedback-release rules.
4. View performance.
5. Eventually practice weak topics through personalized quizzes.

## 4. Business Rules Discussed

- **Human-in-the-loop:** AI-generated questions must not automatically become official questions. Professor approval is the final academic decision.
- **Question lifecycle:** Generated → validated → professor review → approved/rejected/edited → question bank.
- **Assignment targets:** Whole class or selected students.
- **Attempt locking:** The discussed rule was to lock an official quiz after the student's first attempt. Confirm the exact retry/resume behavior in the requirements before implementation.
- **Score separation:** Practice scores and official assessment scores must remain separate.
- **Feedback release:** Consider configurable release modes such as immediate, after submission, after quiz closure, or professor-controlled.
- **Personalization:** Start with explainable rules rather than a trained recommendation model.

## 5. Recommended Technology and Architecture

The recommended direction for the academic MVP is a **Spring Boot modular monolith**, not an immediate microservices deployment.

### Backend modules (suggested)

- Authentication and users
- Professor/student management
- Classes
- Content/document processing
- RAG/retrieval
- AI generation
- Question bank
- Quiz and assignment
- Attempts and evaluation
- Analytics
- Personalization (future)

### Data storage

**PostgreSQL** for relational application data.

**pgVector** is a practical candidate for embedding storage and similarity search because it keeps relational data, document/chunk metadata, and vectors within the PostgreSQL ecosystem. A separate vector database should be introduced only if measured scale or operational needs justify it.

## 6. RAG Pipeline

```text
PDF/Text
   ↓
Text Extraction
   ↓
Chunking
   ↓
Embedding Model
   ↓
Vector Storage (candidate: pgVector)
   ↓
Semantic Retrieval
   ↓
Relevant Source Context
   ↓
LLM Prompt
   ↓
Structured MCQ Output
   ↓
Validation and Quality Review
```

RAG is preferred for the MVP because it can ground generation in course-specific material that changes over time, provides source traceability, and is more feasible than training a model from scratch.

Fine-tuning an open-source model can be explored as future work. Do not claim that RAG eliminates hallucinations; retrieval and source-grounding still require validation.

### Suggested MCQ fields

- Question stem
- Options
- Correct answer
- Explanation
- Topic
- Difficulty estimate
- Source document/chunk reference
- Generation/evaluation metadata

Maintain source references so professors can inspect the context supporting a question.

## 7. AI vs Deterministic Responsibilities

### Appropriate AI responsibilities

- Understanding source content.
- Generating question stems and distractors.
- Producing explanations.
- Estimating topic and difficulty.
- Assessing semantic and pedagogical quality.

### Application-logic responsibilities

- Authentication and authorization.
- Assignment rules.
- Attempt lifecycle and locking.
- Submission handling.
- Marks calculation.
- Transactions and persistence.
- Access control and business-rule enforcement.

**Do not use an LLM to calculate marks for ordinary MCQ answers.** Scoring should be deterministic and testable.

## 8. MCQ Quality Evaluation

The quality dimensions discussed are:

1. Correctness
2. Relevance to source material
3. Clarity
4. Answerability
5. Distractor quality
6. Difficulty appropriateness

Possible evaluation flow:

```text
Generated MCQ
     ↓
Schema Validation
     ↓
Deterministic Checks
     ↓
AI-Assisted Quality Evaluation
     ↓
Flag / Pass / Needs Review
     ↓
Professor Review
     ↓
Approved Question Bank
```

Potential structured evaluation fields include dimension scores, overall assessment, feedback, and source-grounding notes. Thresholds and the final output schema are still to be decided.

An LLM-as-a-Judge can assist but should not be treated as ground truth. Professor review remains the final approval step.

## 9. Research Foundation: Automatic Question Generation (AQG)

### Kurdi et al. (2020)

**“A Systematic Review of Automatic Question Generation for Educational Purposes.”**

Use this as a foundational review of AQG research. Its literature window covers approximately 2015 to early 2019, so it should not be presented as a survey of modern LLM-based AQG.

A generic pipeline extracted from the literature review work:

- **Phase I — Content Identification and Selection:** Identify relevant concepts, entities, statements, and relationships.
- **Phase II — Item Construction:** Construct the question stem, answer, and distractors.
- **Phase III — Quality Assurance and Refinement:** Evaluate and improve correctness, relevance, clarity, answerability, distractors, and difficulty.

### Anwar et al. (2026)

Discussed as a modern survey for LLM-based MCQ generation, methodology evolution, RAG, evaluation, and open research issues. Verify the publication metadata and paper contents directly before citing it in a final academic submission.

## 10. Research Gap: The Evaluation Bottleneck

A key finding from the research discussions:

> Producing a grammatically valid MCQ is not the same as producing a pedagogically valid MCQ.

Traditional text-overlap metrics such as BLEU and ROUGE, and semantic similarity measures such as BERTScore, can be useful for some comparisons but do not adequately establish factual correctness, answerability, distractor quality, difficulty appropriateness, or psychometric validity.

This is the **evaluation bottleneck**.

The project should therefore emphasize the combination of:

```text
Source-grounded generation
        +
Automated quality assessment
        +
Professor-in-the-loop review
```

Do not claim that the system solves educational evaluation generally. State the specific quality dimensions implemented and evaluate them with a defensible methodology.

## 15. Broader Fury Platform Notes (Separate from the Academic MVP)

Other project conversations also covered a broader Fury API Gateway/BFF architecture. These decisions should not automatically become requirements for the academic quiz MVP.

### Documented decisions

- Request tracing: support `X-Request-ID` and `traceparent`; generate `X-Request-ID` when absent.
- JWT: validate external JWTs, strip them at Fury, and issue an internal signed JWT for downstream services.
- Internal JWT claims: `sub`, `tenantId`, `role`, `source`, `aud`, `iat`, `exp`, `jti`, with optional `scope`.
- Authorization: coarse route-level checks at Fury; resource-level authorization downstream.
- Tenant identity: derive from JWT, not a trusted client-supplied tenant ID.
- Idempotency: use `Idempotency-Key` for critical mutations such as exam submission and payments; Redis may support gateway-level idempotency.
- Upload URL endpoint: `POST /api/v1/files/upload-url`; default presigned URL TTL of 10 minutes.
- Pagination: cursor-based, default page size 20, maximum 100.
- Rate limits: anonymous 100/min/IP; authenticated 300/min/user; exam submission 10/min/user.
- Rate-limiting algorithm: Token Bucket with Redis; fail closed for critical endpoints and fail open for ordinary endpoints if Redis fails.
- Response envelope: `{ success, data, error, meta }`.
- Dashboard aggregation: `GET /api/v1/dashboard` fans out in parallel to Groot (profile), Stark (assessments), and Rocket (analytics); partial failure returns a partial response plus warnings.
- Service discovery: Kubernetes/DNS.
- Resilience: per-downstream circuit breakers and endpoint-specific retries, maximum two retries.
- Barton proctoring WebSocket: dedicated exam-session token with `aud=barton`.
- Login/refresh/logout routes exposed by Fury, with authentication delegated to Rogers.
- Frontend and Fury were expected to share a domain, with `SameSite=Strict`.
- Access-token revocation was discussed as allowing a revoked token to remain usable until expiry, with a target access-token TTL of 15 minutes.
